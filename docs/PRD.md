# 송학구이 통합 백오피스 PRD

- 상태: 초안 v0.2 (사장님 답변 반영)
- 작성일: 2026-10-18
- 일정: [백오피스-일정](https://claude.ai/artifact/FBr7cVgYZkooWC5kU37Uex) (2026-10-18 ~ 2026-11-28, MVP 4주 + 개선 2주, 일요일 시작 주)
- 결정 기록: [decisions.md](decisions.md)

> 이 문서는 공개 저장소에 올라갈 수 있다. 실제 거래처명, 직원 이름, 매출 금액은 쓰지 않는다. 예시는 "정산처 A", "직원 1"처럼 적는다.

## 1. 배경

송학구이는 두 개의 자체 웹앱으로 운영하고 있다.

| 앱 | 하는 일 | 쓰는 사람 | 저장소 |
|---|---|---|---|
| 발주 관리 (songhak-inventory) | 직원이 식자재 발주를 요청하고 관리자가 처리 | 직원, 관리자 | Firestore |
| 정산 관리 (songhak-hosting) | 정산처별 주문 입력, 월별 정산, 직원 근무·급여 계산 | 사장님 | Realtime Database |

두 앱 모두 잘 쓰이고 있지만 다음 문제가 있다.

1. **데이터가 따로 있다.** 매출(정산)과 비용(발주)을 한 화면에서 볼 수 없어, 이번 달 매출에서 식자재 비용이 얼마나 빠졌는지 알려면 두 앱을 오가며 직접 계산해야 한다.
2. **기록이 남지 않는다.** 발주 앱은 7일이 지난 발주를 자동 삭제한다. 지난달에 무엇을 얼마나 발주했는지 확인할 수 없다.
3. **과거 금액이 바뀐다.** 정산 앱은 주문에 단가를 저장하지 않고, 화면을 열 때마다 현재 메뉴 가격으로 다시 계산한다. 메뉴 가격이나 할인율을 바꾸면 이미 끝난 달의 정산 금액도 함께 바뀐다.
4. **동시에 쓰면 덮어쓴다.** 정산 앱은 저장할 때마다 전체 데이터를 통째로 덮어쓴다. 두 기기에서 동시에 입력하면 한쪽 입력이 사라질 수 있다.
5. **원하는 숫자를 바로 꺼낼 수 없다.** "이번 달 정산처 A 합계"나 "지난 3개월 직원별 근무시간" 같은 질문에 답하려면 화면을 여러 번 옮겨 다니며 합산해야 한다.
6. **보안이 약하다.** 발주 앱의 관리자 비밀번호가 배포된 코드에 그대로 들어 있고, 게시판 비밀번호는 평문으로 저장된다.

## 2. 목표

1. 두 앱의 데이터를 하나의 관계형 DB에 모으고, 지워지거나 바뀌지 않는 기록으로 쌓는다.
2. 사장님이 한 화면에서 매출, 정산, 발주, 인건비를 본다.
3. 자연어로 질문하면 DB에서 숫자를 찾아 답하고, 어떤 쿼리로 찾았는지 보여 준다.
4. 월말 정산서와 주휴수당 리포트를 자동으로 만든다.
5. 기존 두 앱은 지금처럼 계속 쓴다. 백오피스 때문에 현장 업무가 바뀌지 않게 한다.

### 하지 않는 것 (이번 범위 밖)

- 기존 두 앱을 대체하거나 입력 기능을 옮기는 일 (데이터는 Firebase → Postgres 단방향)
- POS·카드사·세무 시스템 연동
- 재고 수량 관리 (발주 앱에도 재고 수량 데이터는 없다)
- 모바일 앱 (반응형 웹으로 대응)

## 3. 사용자

| 사용자 | 하는 일 | 권한 |
|---|---|---|
| 사장님 | 인건비·정산 확인, 매달 1일 정산서 인쇄, 자연어 질의 | 전체 조회, 설정 |

## 4. 기능

우선순위: **P0** 없으면 출시하지 않음 / **P1** 이번 일정 안에 / **P2** 시간이 남으면

### 4.1 데이터 동기화

| ID | 기능 | 우선순위 |
|---|---|---|
| S1 | Firestore(발주)와 RTDB(정산) 데이터를 Postgres로 가져오는 스크립트 | P0 |
| S2 | 여러 번 실행해도 중복이 생기지 않음 (원본 ID 기준 upsert) | P0 |
| S3 | 하루 1회 자동 실행 (새벽). 발주는 7일 뒤 삭제되므로 실패가 이어지면 바로 알림 | P0 |
| S4 | 발주 앱에서 삭제된 발주도 백오피스에는 남김 | P0 |
| S5 | 가져온 시점의 단가를 주문 항목에 함께 저장 (이후 가격이 바뀌어도 과거 금액 고정) | P0 |
| S6 | 동기화 결과(건수, 실패, 소요 시간) 기록과 실패 알림 | P1 |

### 4.2 대시보드

| ID | 화면 | 내용 | 우선순위 |
|---|---|---|---|
| D1 | 홈 | 사장님이 가장 먼저 보고 싶은 세 가지: ① 이번 급여 기간 인건비(직원별·합계) ② 정산처별 이번 달 정산 금액 ③ 발주 목록(최근순, 미처리 표시). 인건비는 17일~16일, 정산은 1일~말일이라 기간을 각 카드에 표시 | P0 |
| D2 | 정산 | 기간·정산처별 주문 내역과 합계, 기본가/할인가 구분 | P0 |
| D3 | 인건비 | 직원별 근무시간, 기본급, 주휴수당, 합계 (정산 기간은 전월 17일 ~ 당월 16일) | P0 |
| D4 | 발주 | 기간·품목·요청인별 발주 내역과 금액 | P1 |
| D5 | 손익 요약 | 매출 − 발주 비용 − 인건비, 월별 추이 | P1 |
| D6 | 동기화 상태 | 마지막 동기화 시각, 건수, 오류 | P1 |

### 4.3 AI 기능

| ID | 기능 | 우선순위 |
|---|---|---|
| A1 | 자연어 질의: 질문 → SQL 생성 → 실행 → 답변. 답변 아래에 실행한 SQL과 결과 표를 함께 보여 줌 | P0 |
| A2 | 발주량 추천: 쌓인 발주 기록을 바탕으로 이번 주 품목별 발주량 제안 | P2 |

A1 안전장치:
- SELECT 권한만 있는 DB 계정으로 실행한다. 프롬프트로 막는 것이 아니라 DB 권한으로 막는다.
- 허용한 뷰만 조회할 수 있게 하고, 실행 시간과 반환 행 수에 상한을 둔다.
- SQL이 실패하면 오류를 보고 고쳐서 다시 시도한다. 최대 2회까지 재시도한 뒤에도 실패하면 "답을 찾지 못했다"고 말한다. 추측한 숫자로 답하지 않는다.
- 질문 20개로 이루어진 평가 세트를 만들어 정답률을 측정한다.

## 5. 데이터

### 5.1 흐름

```
발주 앱 ─ Firestore ─┐
                     ├─ 가져오기 스크립트 (정기 실행) ─→ Postgres ─→ FastAPI ─→ Next.js 대시보드
정산 앱 ─ RTDB ──────┘                                    │
                                                         └─ 읽기 전용 계정 ─→ 자연어 질의 에이전트
```

### 5.2 주요 테이블 (초안, ERD는 2주차에 확정)

| 영역 | 테이블 | 비고 |
|---|---|---|
| 정산 | places, menus, menu_options, place_menu_price_types, sales_orders, sales_order_items | 주문 항목에 당시 단가 저장 |
| 인건비 | employees, work_logs | 시급은 기간별 이력으로 관리 |
| 발주 | supply_categories, supply_items, requesters, supply_orders, supply_order_items | 원본에서 삭제돼도 유지 |
| 설정 | settings_history | 할인율, 최저시급의 변경 이력 |
| 운영 | sync_runs | 동기화 실행 기록 |

### 5.3 계산 규칙 (정산 앱에서 옮겨 올 것)

- 할인가 = 메뉴 가격 × (1 − 할인율/100), 원 단위 반올림
- 정산처마다 메뉴별로 기본가 또는 할인가를 적용한다
- 옵션(곱빼기 등)은 기본가에 추가금을 더한다. 2026-10-19부터 정산 앱에서 옵션을 한 번 누르면 "옵션 붙은 메뉴 1그릇"이 된다 (`full: true`, 기본가와 추가금을 각각 할인). 그 전 주문은 "기본 메뉴 1 + 옵션 1(추가금만)"으로 저장돼 있어 두 방식을 모두 계산한다
- 직접 입력 항목(추가 식대 등): 입력한 금액 그대로. 할인은 기본으로 적용하지 않고, 체크한 경우에만 적용한다
- 정산처 정산 기간: 달력 기준 1일 ~ 말일. 매달 1일에 지난달 정산서를 전달한다
- 근무시간 = 종료 − 시작 − 휴게
- 급여 정산 기간: 전월 17일 ~ 당월 16일
- 주휴수당: ISO 주 기준으로 주 15시간 이상이면 min(주 근무시간/40, 1) × 8 × 시급. **한 주의 주휴수당은 한 달에만 넣는다.** 급여 기간 경계(16일/17일)에 걸친 주는 그 주의 일요일이 속한 급여 기간에 넣는다 (2026-10-18 확정)

### 5.4 과거 가격 처리

원본에 주문 당시 단가가 없어서, 가격이 바뀌기 전의 주문도 지금 가격으로 계산된다. 알려진 변경은 다음과 같다.

| 변경 | 내용 | 시점 |
|---|---|---|
| 메뉴 가격 인상 | 육회비빔밥 8,000원 → 8,500원 | 2026년 7월 중순쯤 |
| 메뉴 가격 인상 | 물냉면 6,000원 → 6,500원 | 2026년 7월 중순쯤 |
| 메뉴 가격 인상 | 비빔냉면 7,000원 → 7,500원 | 2026년 7월 중순쯤 |
| 정산처 할인 해제 | 정산처 1곳, 10% 할인 → 할인 없음 | 2026년 9월 |

정산 앱은 2026년 7월 초에 배포됐으므로, 가격 인상의 영향을 받는 주문은 7월 초~중순의 약 2주치다. 할인 해제의 영향을 받는 주문은 해당 정산처의 7월 초~9월 해제일까지다. 두 날짜 모두 7월·9월 정산서 인쇄본과 대조해 확정한다.

처리 방침:
- 동기화를 시작한 뒤의 주문은 그날의 단가를 저장한다. 이후로는 가격이 바뀌어도 과거 금액이 변하지 않는다.
- 동기화 이전 주문은 현재 가격으로 가져오되, 금액에 "추정" 표시를 붙인다.
- 변경 시점은 사장님이 보관한 지난 정산서 인쇄본과 대조해 찾는다. 시점을 찾으면 가격 이력 테이블에 넣고 그 이전 주문을 다시 계산한다.

## 6. 비기능 요구사항

- **정확성:** 같은 기간의 정산 합계와 인건비가 기존 앱 화면과 1원 단위까지 일치해야 한다. 차이가 나면 원인을 문서로 남긴다.
- **보안:** 비밀키는 서버 환경 변수에만 둔다. HTTPS 필수. 운영 데이터는 로그인 없이 볼 수 없다.
- **복구:** Postgres를 매일 백업하고 복원 절차를 한 번 이상 실제로 해 본다.
- **사용성:** 사장님이 휴대폰으로 홈과 정산 화면을 확인할 수 있어야 한다.

## 9. 열린 질문

### 남은 질문

1. 과거 단가 보정: 가격 인상(7월 중순쯤)과 할인 해제(9월)의 정확한 날짜. 지난 정산서 인쇄본과 대조해 찾는다. 찾지 못하면 해당 기간 금액은 "추정"으로 둔다.
