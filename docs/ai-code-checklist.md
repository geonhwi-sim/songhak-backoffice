# AI 코드 검증 체크리스트

이 프로젝트의 코드는 대부분 AI 코딩 도구(Claude Code)와 함께 썼습니다. AI가 쓴 코드는 그럴듯해 보여도 틀릴 수 있어서, 합치기 전에 아래 항목을 확인했습니다. 항목마다 이 프로젝트에서 실제로 잡아낸 사례를 붙였습니다.

## 1. 숫자는 코드 밖의 기준과 맞춘다

AI가 쓴 계산 코드는 테스트를 통과해도, 테스트가 같은 오해 위에 서 있으면 함께 틀립니다. 그래서 정답을 코드 밖에서 가져옵니다.

- [ ] 기존 시스템의 결과와 1원 단위까지 비교했다.
- [ ] 기존 시스템도 틀릴 수 있으니, 외부 기록(통장 결제액, 실제 지급액)과도 비교했다.
- [ ] 합계만 보지 않고 단위(주문 한 건, 주 하나)까지 펼쳐 봤다.
- [ ] 차이가 남으면 근거 없이 맞추지 않고 차이로 기록했다.

> **잡은 것:** 인건비 합계는 기존 앱과 같았지만, 주 단위로 펼치자 급여 기간 경계 주의 주휴수당이 두 번 들어가 있었다. 정산에서는 7월 금액이 지운 옵션 때문에 부풀어 있었고, 통장 결제액과 대조해 할인 종료일 오류와 빠진 주문 항목을 찾았다. ([디버깅 기록 1·2](debugging.md))

## 2. 테스트는 경계값과 실패 경로를 본다

- [ ] 정상 입력만이 아니라 경계값(빈 값, 최대 길이, 월·기간 경계)을 넣었다.
- [ ] 실패해야 하는 경우가 실제로 실패하는지 확인했다(권한 없음 → 401, 잘못된 입력 → 422).
- [ ] 실패했을 때 부작용이 없는지 확인했다(잘못된 질문은 AI를 부르지 않고 질문 횟수도 쓰지 않는다).
- [ ] 테스트가 깨지면 코드와 테스트 중 무엇이 맞는지 이유를 정한 뒤에 고쳤다. 테스트를 통과시키려고 기대값부터 바꾸지 않았다.

> **잡은 것:** 공백만 있는 질문이 길이 검사를 통과하는지 테스트하다가, 공백을 지우는 순서가 길이 검사보다 먼저여야 한다는 것을 확인했다. 데모 로그인에 빈 비밀번호를 넣는 테스트는 401에서 422로 바뀌었는데, 입력 검증을 앞에 둔 의도된 변화라서 테스트를 고쳤다.

## 3. 권한은 프롬프트가 아니라 시스템이 막는다

- [ ] AI가 실행하는 SQL은 읽기 전용 DB 계정으로 돌린다. 쓰기, 원본 테이블 조회, 오래 걸리는 쿼리(5초 넘게)는 DB가 거절한다.
- [ ] "하지 마"라고 프롬프트에 적은 것만으로 안전하다고 보지 않았다. 직접 쓰기·원본 조회·임시 테이블 SQL을 넣어서 막히는지 확인했다.
- [ ] 외부 데이터는 읽기 역할만 있는 서비스 계정으로 가져온다. 키가 새어도 원본을 바꿀 수 없다.
- [ ] 로그인이 필요한 API는 로그인 없이 부르면 401이 나는지 하나씩 확인했다.

## 4. 보안은 도구로 한 번, 눈으로 한 번 본다

- [ ] 의존성 취약점: `pip-audit`, `npm audit`. 경고가 나오면 실제 결과물에 들어가는지 확인한다.
- [ ] 비밀값: 전체 커밋 기록에 키·토큰·비밀번호·실제 이름이 없는지 확인했다. `.env`, 실데이터 폴더는 추적하지 않는다.
- [ ] 입력 길이 상한(질문 300자, 비밀번호 128자)을 서버에서 검사한다. 화면의 제한만 믿지 않는다.
- [ ] 바깥에 열린 포트를 직접 확인했다.

> **잡은 것:** npm 경고 6건은 모두 개발용 CLI의 하위 패키지였고, 빌드 결과물에 들어가지 않는 것을 확인한 뒤 개발 의존성으로 옮겼다. 계정별 잠금만으로는 한 IP가 여러 이메일을 번갈아 시도하는 것을 못 막는다는 점을 발견해 IP당 제한을 추가했다.

## 5. AI 기능은 평가 세트로 잰다

- [ ] 답을 눈으로 몇 번 보고 끝내지 않고, 정답이 있는 평가 세트(20문항)로 잰다.
- [ ] 정답은 값이 아니라 정답 SQL로 둔다. 데이터가 늘어도 평가 세트를 고칠 필요가 없다.
- [ ] 프롬프트나 모델을 바꾸면 평가를 다시 돌리고, 정답률·시간·비용을 함께 적는다.
- [ ] 사용자가 답을 검증할 수 있게 실행한 SQL과 결과 표를 함께 보여 준다.
- [ ] 사람도 틀렸던 복잡한 계산(주휴수당)은 AI가 매번 다시 계산하지 않게, 검증된 계산 결과를 읽게 한다.

## 6. 화면은 실제 브라우저로 본다

- [ ] 빌드가 성공했다고 끝내지 않고, 실제 데이터로 화면을 열어 본다(데스크톱·모바일).
- [ ] 오류 화면도 직접 만들어 본다(잘못된 입력, 깨진 요청).

> **잡은 것:** 질문 결과 표의 제목이 `place_name`, `total_amount` 같은 DB 컬럼 이름 그대로 나왔다. 한글 제목으로 바꾼 뒤에도 `order_count`가 빠져 있었다. 깨진 JSON을 보내자 "입력값을 확인해 주세요: 1"이라는 엉뚱한 메시지가 나와서 따로 처리했다.

## 7. 스키마와 배포는 한 번 더 확인한다

- [ ] 마이그레이션은 자동 생성된 파일을 읽어 본 뒤 적용하고, `alembic check`로 모델과 DB가 같은지 확인한다.
- [ ] 배포 설정은 같은 구성(자체 서명 인증서)으로 로컬에서 먼저 띄워 본다.
- [ ] 배포 후에는 모든 주소(운영·데모)에 직접 들어가 맞는 화면이 나오는지 확인한다.

> **잡은 것:** 컬럼에 붙인 CHECK 제약은 자동 생성이 빠뜨려서, 테이블 단위로 옮기는 규칙을 만들었다. 제약 이름이 겹친 마이그레이션도 직접 고쳤다. 로컬 배포 시험에서 화면만 502가 나는 것을 잡았고, 실제 배포 후에는 데모 주소에 운영 로그인 화면이 뜨는 것을 직접 들어가 보고 발견했다. ([디버깅 기록 3](debugging.md))

## 8. 모르는 것은 확인하고, 결정은 기록한다

- [ ] AI가 쓴 라이브러리 사용법이 낯설면 공식 문서에서 확인한다.
- [ ] 이유가 있는 선택은 [decisions.md](decisions.md)에 대안과 함께 적는다. 나중에 AI가 같은 코드를 다시 바꾸려 할 때 근거가 된다.
- [ ] 원본 데이터는 덮어쓰지 않고, 보정은 따로 기록해 되돌릴 수 있게 한다.
